# v0.5.0：战斗 SL 重放（首版）

本版不依赖 BaseLib、RitsuLib 或 CombatSolver。仅参考 CombatSolver 使用原生行动队列的方式，未集成求解器。

## 如何使用

1. 完全退出游戏后更新模组，启动确认 v0.5.0。进入单人战斗，左侧出现“SpireReplay · 战斗重放”面板，可收起。
2. 手动进行几回合，保存退出到主菜单，再继续同一存档（本模组不会自动执行 SL）。
3. 面板选择第几次尝试，以及停止回合。选择“第 3 回合开始时停止”表示自动执行前两回合，到第三回合交还操作权。
4. 点击“开始重放”。支持出牌、目标、使用/丢弃药水、结束回合及常规卡牌选择。随时点击“停止”；已经开始的动作仍按游戏规则结算，不会倒带。
5. 如果已手动执行了一部分相同操作，可以从匹配的操作前缀继续；发生分歧会拒绝继续，需要 SL。

## 保存规则

新的战斗文件放在 `user://SpireReplay/recordings/battles/<开局标识>/<战斗标识>/`。存档开局时间、种子、角色和难度组成开局身份；幕、楼层、房间、遭遇和战斗序号组成战斗身份。SL 和完全退出游戏后均可读取之前的尝试。

战斗进行期间，每次尝试各有一个 JSON，面板显示尝试序号、回合数与操作数。战斗胜利或失败结算后先保存当前文件，再删除该战斗的旧尝试文件，保留最后一次全部操作及 AttemptNumber（累计尝试编号）。其他开局和旧版数据不清理。战外 activities.json 暂仍按原来的会话目录保存；整局事件覆盖、统一有效路线和导入码将在后续实现。

新增 replay_action 保存原生输入动作与 64 字符状态校验码，避免每步保存完整手牌。自动出牌、重复效果仍是战斗结果记录，不会再次作为玩家输入执行。

## 当前边界

- 只支持 v0.5.0 新录制的战斗尝试；旧版 JSON 保留但不可直接自动重放。
- 重放使用原生队列和局部选牌接口，不修改随机数。校验码包含牌堆身份、升级等级、生命/格挡/能力、能量/星能、药水和整局随机数流状态；不代表覆盖所有其他 Mod 的隐藏状态。
- 卡牌/目标/状态不匹配、重复候选无法唯一识别、游戏异常或等待超过 30 秒时停止。不支持的非卡牌选择需手动处理。
- 开战时已经打开的选牌弹窗，请先按原尝试手动选完，再开始重放。撤销结束回合的尝试暂不支持重放。
- 所选记录耗尽时提前停止；要打到第 N 回合，该尝试必须记录到那里。停止不会撤销已执行的操作，也不会强行打断正在结算的动画。
- 首轮验证：编译、22 个真实游戏方法的 Harmony 绑定、归档隔离与清理、JSON 重放顺序、状态/目标分歧检测测试；真实游戏 UI 布局和完整多回合重放尚待实机试用，不声称已验证。

# SpireReplay 0.3.0

无需 BaseLib。启用 Mod 后，自动将单人战斗记录为本地 JSON；没有额外按钮。

## 记录位置

游戏的 `user://SpireReplay/recordings/<session>/` 目录。
Windows 通常为 `%APPDATA%\SlayTheSpire2\SpireReplay\recordings`。
游戏日志中搜索 `Recording battle to` 可以找到实际完整路径。

每场战斗一个 `battle-编号-floor-楼层-唯一编号.json` 文件。
同目录新增 `activities.json`：记录战斗外的选择和战后奖励，使用 `battleId` 关联对应战斗。
v0.3.0 同时核对章节、总楼层、房间编号和房间实例；商店或火堆不会再误关联上一层战斗。
操作记录包含 `act`、`totalFloor`、`roomType`。未关联到本会话战斗的操作不写 `battleId`。
战斗中的二次选牌和药水操作直接写进战斗文件，不在两份文件里重复保存。
每次新开局或重新加载存档使用新的 session 目录，SL 重打不会覆盖旧记录。
相同种子不意味着相同一局；比较时还需检查角色、难度、游戏版本等。
战斗编号来自该局已访问房间中的战斗计数，包含事件内战斗。

## 本版记录内容

- 种子、角色 ID、游戏模式、进阶等级、章节、楼层、战斗编号、遭遇 ID。
- 游戏版本及游戏程序集标识，便于之后判断记录兼容性。
- 战斗开始、玩家/敌方回合开始及结束、结束回合及撤回、胜利或失败。
- 已实际开始结算的出牌及结算完成事件：卡牌 ID/名称/强化等级/战斗实例 ID、目标、能量和星星消耗。
- 自动出牌标记、重复出牌的序号（从 0 开始）及总次数。
- 仅在战斗初始化和玩家回合开始保存手牌、能量、星星及场上生物快照。
- 二次选牌结果（如头槌、弃牌、升级、选牌生成）：选中的卡牌和原始选项索引。
- 药水使用开始、完成、目标和使用前的栏位（从 0 开始），以及丢弃药水。
- 奖励候选项、选中卡牌/替代奖励、领取成功与否、关闭奖励时跳过的剩余项、重掷后选项。
- 商店购买卡牌、遗物、药水、删牌的尝试和结果：商品、报价、金币前后变化及失败原因。
- 获得药水的尝试和结果：覆盖炼制药水、奖励和商店；记录当时药水数量/容量及游戏返回的失败原因。
- 火堆选项和执行结果（包括取消升级），记录生命值前后及净变化。
- 实际卡牌升级前后的等级、名称和实例/牌组位置；过滤不在牌堆中的预览卡。

`playerTurn` 是玩家回合数；`round` 是整场战斗轮数，额外回合时两者可能不同。
`card_play_started` 和 `card_play_finished` 是同一次效果的两个阶段，不要算成两次出牌。
schemaVersion 2 的 finished 事件只用 `data.startedSequence` 引用 started 事件，不重复卡牌详情。
选牌事件中的 `sourceCardPlaySequence`（如果存在）指向当前战斗文件内触发它的出牌。
`player_choice` 是同步层的原始选择，`cards_selected` 是选牌接口解析后的结果，不能当成两次操作。
卡牌奖励的 `reward_card_chosen` 记录点击结果，实际领取是否成功以 `reward_selection_finished` 为准。
领取返回 false 表示取消或未获得，不一定最终跳过；`rewards_closed` 中的 skipped 才表示奖励集结束后未领取。
涉及异步动作的开始与完成事件通过 `operationId` 关联；跨越战斗结束时可能分布在两个文件中。
商店的药水获得记录通过 `shopOperationId` 关联购买操作；火堆升级通过 `restOperationId` 关联火堆选项。
卡牌费用在 started 事件之前已支付，手牌中该牌通常也已移入打出区。
`end_turn.data.source` 区分玩家结束回合动作与游戏效果触发的结束回合。
无效出牌、取消拖牌不会记作成功出牌。

## 保存与限制

每个事件后先写临时文件，再替换 JSON。读取记录不会改动游戏存档。
正常战斗结束时 `status` 为 `won` / `lost`；离开未结束的战斗时为 `interrupted`。
强制关闭游戏或写入失败时，最后有效文件可能仍为 `in_progress`，不能视为完整战斗。
记录错误会写入游戏日志并停止本场记录，不向游戏抛出异常。
同步落盘优先保证第一版的记录持久性；很长的战斗或慢磁盘可能增加耗时。

本版只支持单人模式；v0.5.0 支持下述战斗重放，尚无整局导入与地图路径重放。
只覆盖游戏标准选牌、药水和奖励接口；其他 Mod 自己实现且绕过这些接口的 UI 需要单独适配。
索引型的非卡牌选择保留原始索引，不保证拥有完整候选项说明。
因此这些 JSON 还不是可直接用于完整复现一局的脚本。
本 Mod 不改写卡牌、伤害、随机数或游戏存档。

## 手动验收

1. 启动游戏，确认 Mod 显示 v0.4.1，进入一场单人战斗。
2. 打出一张指定目标的攻击牌，再打出一张防御牌，然后结束回合。
3. 在记录目录确认 JSON 已出现，对照卡牌名称、目标和回合数。
4. 赢得战斗后确认 `status` 为 `won`。
5. 另开一场战斗，中途返回主菜单再继续；确认旧文件保留，新的战斗文件单独生成。
6. 如有额外回合、自动出牌或重复触发效果，检查对应字段。
7. 使用头槌/弃牌等选牌效果，核对 `player_choice` 和 `cards_selected` 中的卡牌。
8. 使用一瓶药水，确认 potion_use_started/finished 具有相同 operationId，目标与栏位正确。
9. 战后领取金币和一张卡牌，检查 activities.json 中的候选项、选中卡牌及领取成功结果。
10. 测试取消卡牌奖励、跳过剩余奖励、药水栏满时领取失败、SL 后重新领取，确认区别和旧文件保留。

### v0.3.0 新增操作验收

- 商店买遗物/卡牌：检查 `shop_purchase_started/finished`，包含商品、报价和 `success: true`。
- 药水满栏时买药水：检查购买结果 `FailureSpace`，以及获得药水结果 `TooFull`。
- 金币不足时购买：检查购买结果 `FailureGold`；售罄时为 `FailureOutOfStock`（仅游戏仍接受购买尝试时）。
- 药水满栏时打出炼制药水：检查 `potion_obtain_started/finished` 和 `failureReason: TooFull`；开始事件含来源出牌序号。
- 火堆睡觉：检查 `rest_option_started` 的 `optionId: HEAL`，完成事件含成功结果及生命值净变化。
- 火堆升级：检查 `optionId: SMITH`，以及 `card_upgrade_started/finished` 中的实际等级变化和关联操作 ID。
- 打开升级预览后取消：允许有取消的火堆结果，但不应记录预览卡的成功升级。
- 商店和火堆的操作应标明所在楼层/房间类型，不再包含上一场战斗的 `battleId`。

失败原因保留游戏原始枚举名；`goldDelta`/`hpDelta` 是操作期间的净变化，可能包含遗物效果，不能等同于单项费用或基础回血。
旧文件保持原样；旧版漏记的操作无法由升级补回。新的记录从重启游戏加载 v0.4.1 后开始生效。

## v0.4.0 事件与古神选择

- `event_options`：事件 ID、名称、古神标记、页面序号，以及选项索引、稳定文本键、标题、锁定状态和关联遗物。每次页面变化记录一次，不保存重复手牌。

- 初始古神的候选遗物由选项记录提供；最终获得的遗物见 relicsAdded。后续古神使用同一记录流程。
